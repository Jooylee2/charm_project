# Chomi → Charm 디바이스 이식 로드맵

## Context (왜 이 문서인가)

현재 Chomi는 브라우저에서 동작하는 음성 웹앱이다. 목표는 이것을 Meta Muse Charm 형태의
**화면 없는 소형 음성 디바이스**(마이크 + 스피커, 아이가 들고 다니는 형태)에 올리는 것이다.

이 문서는 코드를 바로 바꾸는 것이 아니라, **어떤 하드웨어로 갈지 아직 미정인 상태**에서
세 갈래 경로의 장단점과 단계별 진행 순서, 의사결정 지점을 정리한 **로드맵**이다.

핵심 통찰: 현재 앱은 이미 **UI(브라우저) + 두뇌(Next.js API 라우트)** 로 나뉘어 있다.
세 하드웨어 옵션 모두 `chat` / `tts` / `stt` / `extract-interests` API를 **서버로 유지**하고
클라이언트만 교체하는 구조다. 따라서 **"두뇌를 독립 클라우드 서버로 분리"** 가 모든 경로의
공통 첫걸음이며, 이 단계까지는 어느 하드웨어를 고르든 버려지지 않는다.

---

## 현재 아키텍처 (재사용 자산)

| 레이어 | 현재 구현 | 이식 시 운명 |
|--------|-----------|--------------|
| UI / 상태머신 | `src/app/page.tsx` | 클라이언트 형태에 따라 교체 |
| 오디오 훅 | `src/hooks/useSpeech.ts` (Web Speech STT + AudioContext TTS) | 플랫폼별 재구현 |
| 아바타 / 버튼 | `src/components/*` | 화면 없으면 폐기, 있으면 재사용 |
| **AI 대화** | `src/app/api/chat/route.ts` (Gemini + 프롬프트) | **그대로 재사용 (두뇌)** |
| **TTS** | `src/app/api/tts/route.ts` (Google Cloud) | **그대로 재사용** |
| **STT (서버)** | `src/app/api/stt/route.ts` (Google Cloud) | **그대로 재사용** |
| **관심사 추출** | `src/app/api/extract-interests/route.ts` | **그대로 재사용** |
| 프로필 저장 | `src/lib/profile.ts` (localStorage) | localStorage → 서버 DB로 이전 필요 |

**결론:** API 라우트 4개(두뇌)는 어느 경로에서도 살아남는다. 프로필만 localStorage에서
디바이스가 붙을 수 있는 서버 저장소로 옮기면 된다.

## 하드웨어 경로 비교

| 항목 | 폰 셸 | Raspberry Pi Zero 2 W | ESP32-S3 |
|------|-------|----------------------|----------|
| 프로토 단가 | $0 (기존 폰) ~ $60–100 | $40–50 | $25 (양산 시 $12–15) |
| 개발 난이도 | 가장 쉬움 (며칠) | 중간 (수 주) | 어려움 (펌웨어 새로 작성) |
| 코드 재사용 | ~95% | ~80–90% | ~30% (서버 API만) |
| STT/TTS/LLM | 서버 (현행 유지) | 서버 (온디바이스 STT는 추후 옵션) | 100% 서버 (기기는 오디오 스트리머) |
| 오디오 I/O | 네이티브 (모바일 세션 버그 해소) | ALSA + I2S 마이크/앰프 | 네이티브 I2S (성숙) |
| 배터리 | 좋음 (폰 배터리) | 수 시간 (LiPo + 부스트) | 최고 (딥슬립 + 웨이크워드로 며칠) |
| 제품 완성도 | Charm처럼 안 보임 (테스트용) | 준제품 프로토 | 실제 양산 폼팩터 |

**유사 제품 참고:** rabbit R1·Grimo = 커스텀 SoC + 클라우드 LLM(씬 클라이언트) → Pi/MCU+서버 모델과 동일.
Moflin 등 AI 인형 = ESP32급 MCU + 클라우드 + 온디바이스 웨이크워드 (저가 키즈 음성 완구의 사실상 표준).

## 권장 로드맵 (단계별)

### 0단계 — 두뇌 분리 (모든 경로 공통 · 필수 선행)
- `chat/tts/stt/extract-interests` API를 독립 배포 가능한 클라우드 서비스로 유지·정리
  (지금도 Vercel 서버리스 함수라 사실상 준비됨).
- **프로필 저장을 localStorage → 서버 저장소로 이전** (디바이스에는 브라우저 저장소가 없을 수 있음).
  키: 디바이스 ID 또는 아이 ID. `src/lib/profile.ts`의 함수 시그니처를 유지한 채 백엔드만 교체.
- API 계약(요청/응답 스키마)을 문서화 → 이후 어떤 클라이언트든 이걸 보고 붙임.
- **산출물:** 클라이언트에 독립적인 "Chomi 두뇌 API".

### 1단계 — 폰 셸로 실사용 테스트 (권장 시작점)
- 배포된 웹앱을 Capacitor 또는 PWA로 감싸 Android/태블릿에 설치.
- 얻는 것: 진짜 네이티브 마이크/오디오 API → 현재 모바일 Chrome 세션 버그에서 완전히 해방.
- 목적: **하드웨어를 고르기 전에** 아이 대상 UX(웨이크워드 필요성, 대화 길이, 안전성)를 실측.
- **산출물:** 아이에게 쥐여줄 수 있는 테스트 리그.

### 2단계 — Pi Zero 2 W 프로토타입
- 두 가지 클라이언트 방식 중 택1:
  - (a) Chromium 키오스크로 기존 웹앱 그대로 띄움 (재사용 최대)
  - (b) 헤드리스 Node 클라이언트가 마이크 캡처 → 서버 STT → TTS 재생 (경량)
- 하드웨어: Pi Zero 2 W + I2S 마이크(INMP441) + I2S 앰프/스피커(MAX98357A) + LiPo/충전보드.
- 오디오: ALSA. STT는 신뢰성을 위해 브라우저 Web Speech 대신 **서버 `/api/stt` 사용**.
- 새로 필요한 것:
  - **웨이크워드** (버튼 없는 charm이므로) — Porcupine 또는 openWakeWord.
  - Wi-Fi 프로비저닝 (부모가 집 와이파이 연결하는 절차).
- **산출물:** 전원 켜면 말 걸 수 있는 준제품 프로토.

### 3단계 — ESP32-S3 양산형 (양산 확정 시에만)
- 펌웨어 전면 재작성(C/ESP-IDF): 기기는 오디오 캡처 → WebSocket으로 서버 스트리밍 → 반환 오디오 재생.
- 두뇌는 0단계 API 그대로. 재사용은 서버 계약 ~30%.
- 온디바이스 웨이크워드(ESP-SR/WakeNet), OTA 업데이트, 오디오 버퍼링 스트리밍 설계.
- 배터리 딥슬립으로 며칠 지속 → 실제 키즈 charm에 이상적.
- **산출물:** 저전력·소형 양산 디바이스.

## 이번 문서 범위에서 제외 (별도 결정 필요)
- **개인정보/안전:** 아이 음성이 클라우드로 나감. 온디바이스 STT 여부, 녹음 보관 정책, 부모 동의 UX.
- **웨이크워드 vs 버튼:** charm 폼팩터엔 버튼이 없으므로 always-listening 설계가 필요 → 배터리·프라이버시 영향 큼.
- **다국어(영어) 지원:** 이전에 보류한 항목. STT `lang` + TTS voice 분기 필요.
- **오프라인 동작:** 현재 100% 클라우드 의존. 연결 끊김 시 UX.

## 검증 방법 (각 단계별)
- **0단계:** API를 로컬 curl / Postman으로 호출해 클라이언트 없이 대화 왕복 확인. 프로필 서버 저장/조회 라운드트립 테스트.
- **1단계:** Capacitor 빌드를 실제 Android 기기에 설치 → 연속 대화 5회 이상, 마이크/스피커 정상, 세션 버그 없음 확인.
- **2단계:** Pi에서 전원 인가 → 웨이크워드 → 대화 → TTS 재생 end-to-end. 배터리 지속 시간 실측.
- **3단계:** ESP32 딥슬립 복귀 시간, 스트리밍 지연(마이크→응답 음성), OTA 성공률 측정.

---

## 요약 권장안
**폰 셸로 UX 검증 → Pi Zero 2 W로 준제품 프로토 → 양산 확정 시에만 ESP32-S3로 이전.**
어느 경로든 **0단계(두뇌 API 분리 + 프로필 서버화)** 를 먼저 하면 이후 작업이 버려지지 않는다.
